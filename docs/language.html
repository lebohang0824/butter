Language Guide

A small, implementation-agnostic intent specification language for AI agents.

Butter makes application intent explicit and structured. It describes what must be true and what behavior the implementation should satisfy, while leaving technology choices to the implementation context supplied alongside the specification.

AI integration tip: teach your AI the Butter spec language and its syntax before asking it to help you write a spec. Copy this prompt and give it to your AI agent:

Learn the Butter Specification Language and its syntax from the language guide
at https://butter-jet.vercel.app/language.html
Then help me express application intent without prescribing implementation technology.

Core Philosophy

Butter is an intent specification language for AI agents. Its purpose is to communicate what software is intended to do, what must happen, what must not happen, which constraints apply, and what outcomes are expected.

Butter specifies what must be true; the implementation context specifies how to make it true.

Butter does not attempt to describe every aspect of an implementation. It stays intentionally small: introduce a keyword or construct only when the existing language cannot express an important form of intent clearly.

Before adding syntax, ask: Can this already be expressed clearly using the existing Butter language? If the answer is yes, keep the language unchanged.

Intent and Implementation Context

Keep application intent separate from technology and project decisions. The two belong together when you ask an AI agent to implement a specification, but they serve different purposes.

Butter communicates

  • application intent and business requirements
  • business rules and application-level constraints
  • validation requirements
  • workflows and ordered actions
  • conditions, invariants, and boundaries
  • expected outcomes
  • API and interface contracts, including HTTP endpoints where supported
  • behavior that the implementation must satisfy

Implementation context communicates

  • programming language and framework
  • database technology and libraries
  • infrastructure and deployment environment
  • architecture choices
  • coding conventions and existing project structure
  • technology-specific documentation

Supply implementation-specific information to the AI agent alongside the Butter specification. For example:

Butter specification
        +
"Implement using Laravel + Vue"
        ↓
Laravel/Vue application

Butter specification
        +
"Implement using Django + React"
        ↓
Django/React application

The Butter specification remains the same because the application's intent has not changed.

Syntax

Butter uses strict 2-space indentation per nesting depth: depth 0 = 0 spaces, depth 1 = 2 spaces, depth 2 = 4 spaces, depth 3 = 6 spaces. Comments use # or //.

# Root Application Specification
app MyApp
├── description <string>
├── version <string>
├── rules
│   └── <string>
├── feature <name>
└── endpoint <name> <route>

# Subsystem Feature Block Specification
feature CreateTask
├── description <string>
├── version <string>
├── params
│   └── <name> <type>
└── actions
    └── <string>
        └── enforce <string>

# HTTP Endpoint Contract
endpoint StoreTodo "/todo"
├── description <string>
├── version <string>
├── method <string>
├── params
│   └── <name> <type>
├── responses
│   └── <name>
│       └── <name> <type>
├── actions
│   └── <string>
│       └── enforce <string>
└── returns
    └── <code> <ResponseName|string>

Endpoint header note: <name> is an unquoted, CamelCase, unique identifier. <route> is a quoted string. Two endpoints may not share a <name> even if their routes differ. Endpoint uniqueness is on the name, not the route.

What Butter Can Express

Butter's existing constructs already cover the important forms of application intent. This section explains that scope; it does not introduce new syntax.

Application behavior

Use a feature and ordered actions to describe what the application should do.

feature CreateTask
  description "Creates a task for an assigned user"

  params
    title string
    assignee_id string

  actions
    "Validate title is not empty"
    "Validate assignee_id identifies an existing user"
    "Create a task with a unique identifier"
    "Notify the assigned user"

Business rules

Use the app-level rules block for conditions that apply across the application.

app TaskManager
  description "Manages tasks for individual users"

  rules
    "Users may only access tasks they own"
    "A task cannot be completed until it is assigned to a user"

Workflows

Actions are written in declaration order. Use separate actions for steps that must happen in a particular sequence.

actions
  "Validate the request"
  "Reserve the requested capacity"
  "Create the booking"
  "Notify the customer"

Validation

Use params for accepted input shapes and actions or enforce for conditions that reject invalid input.

params
  email string
  age integer

actions
  "Validate email has the required format"
  "Reject the request when age is below the minimum"
    enforce "The user must meet the minimum age requirement"

Constraints and invariants

Use rules for application-wide invariants and enforce for constraints attached to an action.

"Transfer funds"
  enforce "The source account must retain its required minimum balance"
  enforce "The transfer amount must not exceed the available balance"

Interfaces

Use an endpoint to describe an HTTP contract: route, method, parameters, response schemas, actions, and return mappings.

endpoint GetTask "/tasks/{task_id}"
  method "GET"

  responses
    TaskResponse
      id integer
      title string
      status string

  returns
    200 TaskResponse
    404 "Task not found"

Expected outcomes

Actions and returns describe the result an implementation must produce or guarantee after an operation.

actions
  "Create an invitation with a unique identifier"
  "Send the invitation to the recipient"

returns
  201 InvitationResponse
  409 "An invitation already exists"

Boundaries

Use rules, actions, and enforce expressions for behavior the implementation must not perform when that boundary is part of the application's intent.

rules
  "Users must not access another user's private resources"
  "Deleted resources must not be returned by list operations"

actions
  "Reject the request when the user is not authorized"

Features

A feature declares an application capability: what inputs it accepts and what behavior it provides.

feature ProcessPayment
  description "Validates and records a payment"
  version "1.0.0"

  params
    order_id string
    amount double
    payment_method enum["card", "bank_transfer"]

  actions
    "Validate the payment amount"
    "Verify the payment method is allowed"
    "Record the payment outcome"

Feature rules

  • Feature names are CamelCase; each name must be unique within the spec.
  • Valid names contain letters, digits, underscores, and hyphens.
  • Everything under a feature must be indented.
  • Valid keywords inside a feature are description, version, params, and actions.
  • A blank line is required above a feature, except when it is the first top-level block in the file. If comments appear directly above, the blank line sits above the comments.
  • A feature can be empty — zero params and zero actions is valid.

Rules

The rules block lives under app and declares application-wide intent, business constraints, and invariants that the implementation should respect.

app OrderService
  description "Creates and manages customer orders"
  version "1.0.0"

  rules
    "Customers may only access orders they own"
    "An order cannot be charged for more than its calculated total"
    "Operations that would create duplicate orders must be rejected"

Do not use rules to select implementation technology. Statements such as the following belong in the implementation context or pre-prompt, not in the Butter specification:

"Use Laravel"
"Use React"
"Use PostgreSQL"
"Use Redis"
"Use Python"

How they work

  • Place rules under app, alongside description and version.
  • A blank line is required above the rules block.
  • Each rule is a quoted string on its own line, indented 4 spaces.
  • Rules apply to every feature and endpoint in the spec, not to a single action.

Parameters

Params declare the inputs a feature or endpoint accepts. Each parameter is a name followed by a type, on its own line.

params
  title string
  priority enum["low", "medium", "high"]
  limit integer

Types

TypeExampleNotes
stringname stringDefault when type is omitted.
integercount integerWhole numbers.
doubleamount doubleFloating-point values.
booleanactive booleantrue or false.
enum[...]mode enum["a", "b"]One of a fixed set of values.
array[...]tags array[string]A list of a single element type.

Parameter names are snake_case and must be unique within a feature or endpoint. Inside enum[...], values are quoted strings and each must be unique within the list. array[<type>] accepts one of string | integer | double | boolean as its element type.

Actions

Actions describe the ordered behavior an implementation should perform. Each action is a quoted string.

actions
  "Validate title is not empty"
  "Assign a unique identifier to the new task"
  "Set the creation timestamp"
  "Notify the assigned user"
  "Schedule a reminder for the due date"

How they work

  • Sequential. Steps run in declaration order.
  • Discrete. Keep each action to one behavior. Split complex work into multiple actions.
  • Intent-focused. Describe the required result or behavior, not a preferred library, framework, or database.

Write actions as clear application-level instructions. The implementation context determines how each action is realized.

Enforce

Actions can have enforce expressions as indented children. These are constraints or invariants that must hold for the action to succeed.

"Validate account balance"
  enforce "The source account must retain its required minimum balance"

"Charge payment method"
  enforce "The charge amount must not exceed the order total"
  enforce "The payment method must be verified before charging"

An action describes the behavior; the enforce expression states a condition that must remain true.

Endpoints

An endpoint describes an HTTP interface contract: route, method, parameters, response schemas, ordered behavior, and return mappings.

app OrderService
  description "Creates and retrieves customer orders"
  version "1.0.0"

endpoint CreateOrder "/api/orders"
  description "Validates and creates an order"
  version "1.0.0"
  method "POST"

  params
    customer_id string
    currency string
    dry_run boolean

  responses
    OrderSuccessPayload
      order_id integer
      total_amount double
      currency string

  actions
    "Validate the customer identifier"
    "Calculate the order total"
    "Create the order with a unique identifier"

  returns
    201 OrderSuccessPayload
    200 "Dry run completed"
    400 "Invalid order data"
    500 "Order creation failed"

Rules

  • Route goes in the header: endpoint Name "/path". The parser rejects an unquoted or missing route.
  • method is required and must be one of GET, POST, PUT, DELETE, or PATCH.
  • Valid keywords inside an endpoint are description, version, method, params, responses, actions, and returns.
  • Each endpoint must have a unique name.
  • A blank line is required above each endpoint, except when it is the first top-level block. If comments appear directly above, the blank line sits above the comments.
  • returns status codes must be integers in the range 100–599.
Feature vs Endpoint: Use feature for application behavior. Use endpoint for an HTTP interface contract. They live side by side under app.

Responses

The responses block defines named response schemas. Each response has a PascalCase name and typed fields.

responses
  OrderSuccessPayload
    order_id integer
    total_amount double
    currency string
    line_items array[string]

  ValidationError
    error string
    details string

Response names are CamelCase and must be unique within an endpoint. Field names are snake_case. Any name referenced in returns must be defined here.

Returns

The returns block maps HTTP status codes to response schemas or string payloads.

returns
  201 OrderSuccessPayload
  200 "Dry run completed"
  400 "Invalid order data"
  404
  500 "Order creation failed"

Format

SyntaxMeaning
201 OrderSuccessStatus 201, body matches the OrderSuccess response schema.
400 "Invalid token"Status 400, body is this string.
204Status 204, no body.

Status codes must be integers in the range 100–599 inclusive. Use codes that match the standard HTTP status code registry for meaningful mappings. Response names referenced here must exist in the responses block.

Structural Rules

The compiler enforces structural rules: exactly one app; unique feature, endpoint, param, and enum values; valid types and HTTP methods; status codes in 100–599; and response references defined in the same endpoint. Field presence below is a matter of convention and intent — the compiler does not require the “recommended” items.

app

  • description (Recommended)
  • version (Optional)
  • rules (Optional)
  • feature (Optional, zero or more)
  • endpoint (Optional, zero or more)

feature

  • description (Recommended)
  • version (Optional)
  • params (Optional)
  • actions (Recommended — at least 1, run in order)

endpoint

  • Route in the header, e.g. endpoint <name> "/route" (Required)
  • method (Required — one of POST | GET | PUT | DELETE | PATCH)
  • description (Recommended)
  • version (Optional)
  • params (Optional)
  • responses (Optional)
  • actions (Recommended — at least 1, run in order)
  • returns (Recommended — at least 1)

Full-Stack Example — Task Manager Intent

This example specifies a full-stack application's intent without selecting a technology stack. It includes application behavior, business rules, features, actions, and HTTP endpoints using only existing Butter syntax.

app TaskManager
  description "Manages tasks for individual users"
  version "1.0.0"

  rules
    "Users may only access tasks they own"
    "A task cannot be completed until it is assigned to a user"
    "Operations that would create duplicate tasks must be rejected"
    "Archived tasks cannot be modified or deleted"

feature CreateTask
  description "Creates a task with a title, priority, and optional due date"
  version "1.0.0"

  params
    title string
    description string
    priority enum["low", "medium", "high", "urgent"]
    due_date string
    assignee_id string

  actions
    "Validate title is not empty"
    "Validate assignee_id identifies an existing user"
    "Validate due_date is a valid future date when provided"
    "Create a task with a unique identifier"
    "Set the task status to pending"
    "Notify the assigned user about the new task"

feature ListTasks
  description "Lists and filters the requesting user's tasks"
  version "1.0.0"

  params
    status_filter enum["all", "pending", "completed", "archived"]
    sort_by enum["created", "priority", "due_date", "title"]
    limit integer

  actions
    "Select tasks owned by the requesting user"
    "Filter selected tasks by status_filter"
    "Sort selected tasks according to sort_by"
    "Limit results to the requested count"
    "Return tasks with pagination metadata"

feature UpdateTask
  description "Updates editable attributes of a task"
  version "1.0.0"

  params
    task_id string
    title string
    status enum["pending", "completed", "archived"]
    priority enum["low", "medium", "high", "urgent"]

  actions
    "Look up the task owned by the requesting user"
    "Reject the update if the task is archived"
    "Validate title is not empty when provided"
    "Apply the requested task changes"
    "Set the last-modified timestamp"

feature DeleteTask
  description "Permanently removes a task after confirmation"
  version "1.0.0"

  params
    task_id string
    confirmation string

  actions
    "Look up the task owned by the requesting user"
    "Verify confirmation matches the task title"
    "Reject the deletion if the task is archived"
    "Remove the task"
    "Notify authorized observers about the deletion"

endpoint SaveTask "/api/tasks"
  description "Creates a task through the task API"
  version "1.0.0"
  method "POST"

  params
    title string
    description string
    priority enum["low", "medium", "high", "urgent"]
    due_date string
    assignee_id string

  responses
    TaskResponse
      id integer
      title string
      description string
      priority string
      due_date string
      assignee_id string
      status string

  actions
    "Validate title is not empty"
    "Validate assignee_id identifies an existing user"
    "Reject the request when it would create a duplicate task"
    "Create the task with a unique identifier"
    "Set the task status to pending"

  returns
    201 TaskResponse
    400 "Invalid task data"
    403 "The user may not create a task for that assignee"
    409 "A duplicate task already exists"

endpoint ListTasks "/api/tasks"
  description "Lists tasks through the task API"
  version "1.0.0"
  method "GET"

  params
    status_filter enum["all", "pending", "completed", "archived"]
    sort_by enum["created", "priority", "due_date", "title"]
    limit integer

  responses
    TaskListResponse
      tasks array[string]
      total integer
      next_cursor string

  actions
    "Select tasks owned by the requesting user"
    "Filter selected tasks by status_filter"
    "Sort selected tasks according to sort_by"
    "Limit results to the requested count"
    "Return tasks with pagination metadata"

  returns
    200 TaskListResponse
    400 "Invalid filter or limit"

What Butter Intentionally Does Not Express

Butter is not a programming language, framework, database schema language, deployment language, UI design language, Figma-like design specification, visual styling language, or technology configuration language.

For user interfaces, Butter can express behavioral intent related to an interaction. It does not need to describe exact layouts, colors, typography, spacing, component dimensions, or responsive breakpoints. Communicate those details through design artifacts or implementation context provided alongside the specification.

Butter can express: “A user must be able to filter their tasks by status.”
Butter does not need to express: “Place the filter dropdown 24px from the right edge and use a 14px font.”

The first statement is application intent. The second is a design or implementation concern.
