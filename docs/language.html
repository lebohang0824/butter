Language Guide

Everything you need to write .butter specs — from basic features to HTTP endpoints.

AI integration tip: teach your AI the Butter spec language and its syntax before asking it to help you write a spec. Copy this prompt and give it to your AI agent:

Learn the Butter Specification Language and its syntax from the language guide
at https://butter-jet.vercel.app/language.html
Then help me write a Butter spec.

Syntax

Butter uses strict 2-space indentation per nesting depth: depth 0 = 0 spaces, depth 1 = 2 spaces, depth 2 = 4 spaces, depth 3 = 6 spaces. Comments use # or //.

# Root Application Specification
app MyApp
├── description <string>
├── version <string>
├── rules
│   └── <string>
├── feature <name>
└── endpoint <name> <route>

# Subsystem Feature Block Specification
feature CreateTask
├── description <string>
├── version <string>
├── params
│   └── <name> <type>
└── actions
    └── <string>
        └── enforce <string>

# Synchronous HTTP Endpoint Transport Block Specification
endpoint StoreTodo "/todo"
├── description <string>
├── version <string>
├── method <string>
├── params
│   └── <name> <type>
├── responses
│   └── <name>
│       └── <name> <type>
├── actions
│   └── <string>
│       └── enforce <string>
└── returns
    └── <code> <ResponseName|string>

Endpoint header note: <name> is an unquoted, CamelCase, unique identifier. <route> is a quoted string. Two endpoints may not share a <name> even if their routes differ. Endpoint uniqueness is on the name, not the route.

Features

A feature declares something your system should do. It describes a capability — what inputs it takes and what steps to follow.

feature ProcessPayment
  description "Handles payment transactions"
  version "1.0.0"

  params
    order_id string
    amount double
    payment_method enum["credit_card", "crypto", "bank_transfer"]

  actions
    "Validate routing balance metrics"
    "Apply cryptocurrency transaction surcharge"
    "Flag transaction for manual risk review"

Rules

  • Feature names are CamelCase; each name must be unique within the spec.
  • Valid names: letters, digits, underscores, hyphens.
  • Everything under a feature must be indented.
  • Valid keywords inside a feature: description, version, params, actions.
  • A blank line is required above a feature, except when it is the first top-level block in the file. If comments appear directly above, the blank line sits above the comment(s).
  • A feature can be empty — zero params and zero actions is valid.

Rules

The rules block lives under app and declares app-wide constraints the AI must respect throughout the entire implementation.

app MyApp
  description "Order checkout and payment API"
  version "1.0.0"

  rules
    "Use Node on the backend"
    "Use React on the frontend"
    "Never store plain-text credentials"

How they work

  • Place under app, alongside description and version.
  • A blank line is required above the rules block.
  • Each rule is a quoted string on its own line, indented 4 spaces.
  • Rules apply to every feature and endpoint in the spec — not to any single action.

Parameters

Params declare the inputs a feature or endpoint accepts. Each parameter is a name followed by a type, on its own line.

params
  title string
  priority enum["low", "medium", "high"]
  limit integer

Types

TypeExampleNotes
stringname stringDefault when type is omitted.
integercount integerWhole numbers.
doubleamount doubleFloating-point values.
booleanactive booleantrue or false.
enum[...]mode enum["a", "b"]One of a fixed set of values.
array[...]tags array[string]A list of a single element type.

Parameter names are snake_case and must be unique within a feature or endpoint. Inside enum[...], values are quoted strings and each must be unique within the list. array[<type>] accepts one of string | integer | double | boolean as its element type.

Actions

Actions are the steps the AI must execute — in order, one after another. Each action is a quoted string describing what to do.

actions
  "Validate title is not empty"
  "Assign unique identifier to the new task"
  "Set creation timestamp to current time"
  "Send notification to assigned user"
  "Schedule reminder for due date"

How they work

  • Sequential. Steps run in declaration order. Never in parallel.
  • Deterministic. Same inputs produce the same execution path.
  • Atomic. Each action is one step. Break complex work into multiple actions.

Keep every action to a single step — one discrete operation, nothing more. If an action does several things, split it into separate actions so the AI executes them one at a time and in strict order.

Write actions like you're giving instructions to a developer. Be specific about what to validate, calculate, or create.

Enforce Rules

Actions can have enforce rules as indented children. These are constraints that must hold for the action to succeed.

"Validate routing balance metrics"
  enforce "The payment gateway must have sufficient routing capacity"
  enforce "Failed validations must log the routing error before halting"

"Charge customer payment method"
  enforce "The charge amount must not exceed the order total"
  enforce "The payment method must be verified before charging"

An action always runs. The enforce rule is an invariant — something that must be true for the step to succeed.

Endpoints

An endpoint describes an HTTP API contract: the route, method, parameters, response schemas, execution steps, and return mappings. Everything the AI needs to implement the endpoint is in one block.

app MyApp
  description "Order checkout and payment API"
  version "1.0.0"

endpoint ProcessOrder "/api/checkout/orders"
  description "Validates checkout and processes payment"
  version "1.0.0"
  method "POST"

  params
    checkout_token string
    coupon_code string
    dry_run boolean

  responses
    OrderSuccessPayload
      order_id integer
      total_amount double
      currency string

  actions
    "Verify checkout token is valid and active"
    "Calculate final prices using coupon_code"
    "Authorize payment transaction"

  returns
    201 OrderSuccessPayload
    200 "Dry run completed"
    400 "Invalid checkout token"
    500 "Payment provider timeout"

Rules

  • Route goes in the header: endpoint Name "/path". The parser rejects an unquoted or missing route.
  • method is required and enforced — one of GET, POST, PUT, DELETE, PATCH.
  • Valid keywords inside an endpoint: description, version, method, params, responses, actions, returns.
  • Each endpoint must have a unique name (unique on <name>, not the route).
  • A blank line is required above each endpoint, except when it is the first top-level block. If comments appear directly above, the blank line sits above the comment(s).
  • returns status codes must be integers in the range 100–599.
Feature vs Endpoint: Use feature for business logic. Use endpoint for HTTP API contracts. They live side by side under app.

Responses

The responses block defines named response schemas. Each response has a PascalCase name and typed fields.

responses
  OrderSuccessPayload
    order_id integer
    total_amount double
    currency string
    line_items array[string]

  ValidationError
    error string
    details string

Response names are CamelCase and must be unique within an endpoint. Field names are snake_case. Any name referenced in returns must be defined here.

Returns

The returns block maps HTTP status codes to response schemas or string payloads.

returns
  201 OrderSuccessPayload
  200 "Dry run completed"
  400 "Invalid checkout token"
  404
  500 "Payment provider timeout"

Format

SyntaxMeaning
201 OrderSuccessStatus 201, body matches the OrderSuccess response schema.
400 "Invalid token"Status 400, body is this string.
204Status 204, no body.

Status codes must be integers in the range 100–599 (inclusive); codes outside this range are rejected. The compiler validates the range only — use codes that match the standard HTTP status code registry (e.g. 200, 201, 400, 404, 500) for meaningful mappings.

Response names referenced here must exist in the responses block.

Scope Rules

The compiler enforces structural rules: exactly one app; unique feature, endpoint, param, and enum values; valid types and HTTP methods; status codes in 100–599; response references defined in the same endpoint. Field presence below is a matter of convention and intent — the compiler does not require the "recommended" items.

app

  • description (Recommended)
  • version (Optional)
  • rules (Optional)
  • feature (Optional, zero or more)
  • endpoint (Optional, zero or more)

feature

  • description (Recommended)
  • version (Optional)
  • params (Optional)
  • actions (Recommended — at least 1, run in strict order)

endpoint

  • Route in the header, e.g. endpoint <name> "/route" (Required — the parser rejects an unquoted or missing route)
  • method (Required — one of POST | GET | PUT | DELETE | PATCH; enforced)
  • description (Recommended)
  • version (Optional)
  • params (Optional)
  • responses (Optional)
  • actions (Recommended — at least 1, run in strict order)
  • returns (Recommended — at least 1)

Full Example — Todo App

app TodoApp
  description "A full-featured todo application"
  version "1.0.0"

  rules
    "Use Node on the backend"
    "Use React on the frontend"

feature CreateTask
  description "Creates new tasks with title, priority, and due date"
  version "1.0.0"

  params
    title string
    description string
    completed boolean
    priority enum["low", "medium", "high", "urgent"]
    due_date string

  actions
    "Validate title is not empty"
    "Assign unique identifier to the new task"
    "Set creation timestamp to current time"
    "Set completed status to false"
    "Send notification to assigned user"
    "Schedule reminder for due date"

feature ListTasks
  description "Retrieves and filters tasks based on criteria"
  version "1.0.0"

  params
    status_filter enum["all", "pending", "completed", "archived"]
    sort_by enum["created", "priority", "due_date", "title"]
    limit integer

  actions
    "Query task repository with specified filters"
    "Sort results according to sort_by parameter"
    "Limit results to specified count"
    "Apply pagination metadata to response"

feature UpdateTask
  description "Modifies existing task attributes"
  version "1.0.0"

  params
    task_id string
    title string
    status enum["pending", "completed", "archived"]
    priority enum["low", "medium", "high", "urgent"]

  actions
    "Look up task by task_id"
    "Populate form fields with current task values"
    "Merge provided fields into existing task record"
    "Set last-modified timestamp to current time"
    "Reject update if task is archived"

feature DeleteTask
  description "Removes a task permanently"
  version "1.0.0"

  params
    task_id string
    confirmation string

  actions
    "Verify task_id exists in repository"
    "Verify confirmation matches task title"
    "Remove task record from persistent storage"
    "Broadcast deletion event to connected clients"

endpoint SaveTask "/api/tasks"
  description "Persists a task to the todo API"
  version "1.0.0"
  method "POST"

  params
    title string
    description string
    completed boolean

  responses
    TaskResponse
      id integer
      title string
      description string
      completed boolean

  actions
    "Validate title is not empty"
    "Set completed to false by default"
    "Store task in the database"

  returns
    201 TaskResponse
    500 "Internal server error"

Compile: butter compile todo.butter — produces todo.prompt.md. Use -f json or -f yaml for other formats.
